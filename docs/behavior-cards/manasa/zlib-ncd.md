# Behavior card — ZLIB NCD

Source: `textdistance/algorithms/compression_based.py` (`ZLIBNCD`, via `_BinaryNCDBase` and `_NCDBase`)
Target: `rust/src/algorithms/compression/zlib_ncd.rs`
Original tests: no dedicated fixed-value file, but **is** covered by `tests/original/test_compression/test_common.py`'s shared property tests.

## What it does

Same NCD formula as BZ2 NCD and LZMA NCD:

```text
NCD(a, b) = (C(a+b) - min(C(a), C(b))) / max(C(a), C(b))
```

`ZLIBNCD._compress` calls `codecs.encode(data, 'zlib_codec')` and strips the
first **2 bytes** (the zlib stream header) before measuring length.

## Inputs / options

- No constructor options (`_BinaryNCDBase.__init__` is `pass`). No `qval`.
- Accepts `str` (UTF-8 encoded first) or `bytes` (unchanged).
- `maximum()` is always `1`.

## Edge cases

- Empty/empty: `0.0` (verified below).
- Unlike LZMA, zlib's overhead is small (2-byte header strip vs. LZMA's 14),
  so it discriminates cleanly even on short strings — see worked examples.

## Worked examples — generated, not frozen

`tests/original/` has **no dedicated fixed-value test file** for ZLIB NCD
(unlike BZ2 NCD, which has `test_bz2_ncd.py`). It **is** included in
`test_common.py`'s `ALGS` tuple, so the shared property tests (symmetry,
monotonicity, normalization) do apply and do get exercised — this is a
lighter gap than LZMA's, not a zero-coverage situation.

These worked values were generated by running the actual, unmodified
`textdistance.zlib_ncd` from this repo's own `textdistance/` package:

| left | right | observed |
| --- | --- | --- |
| `''` | `''` | `0.0` |
| `test` | `test` | `0.2` |
| `test` | `text` | `0.4` |
| `test` | `nani` | `0.4` |
| `hello` | `haloa` | `0.45454545454545453` |

Monotonicity holds cleanly here (`0.2 <= 0.4 <= 0.4`), and unlike LZMA,
`test`/`text` and `test`/`nani` are numerically distinguishable in
principle even though they land on the same value for this particular
pair — zlib's smaller header overhead lets real differences show through
better than LZMA's does at this input size.

## Numeric tolerance

No frozen fixed-value tolerance to match exactly, but the shared property
tests in `test_common.py` are exact-equality assertions (not tolerance-based)
for symmetry (`==`) and use `isclose` only for the normalization-sums-to-one
check. The port must satisfy those exactly, in addition to being close to
the generated values above.

## Dependencies / compressor settings

- Python side: stdlib `zlib` via `codecs.encode(data, 'zlib_codec')`,
  default compression settings.
- Rust side: no crate chosen yet. Candidate: `flate2` (widely used,
  supports zlib/deflate/gzip). Goes in `docs/dependency-notes/manasa.md`
  (`MAN-09`) alongside the BZ2 and LZMA candidates.

## Known risks

- Same exact-byte-match risk as BZ2/LZMA: a Rust zlib crate (`flate2`) may
  not produce the same compressed length as Python's `zlib_codec`, even at
  identical compression settings, because default compression level and
  strategy must both match. Document any deviation in `DECISIONS.md` rather
  than chasing byte-perfect parity, per the team's agreed fallback.
- The `[2:]` header-strip is specific to Python's `zlib_codec` framing;
  confirm `flate2`'s raw-deflate vs. zlib-wrapped output modes before
  picking one, since only one of them will have a comparable 2-byte header
  to strip.
- No fixed-value frozen fixture exists, only shared properties — same
  caution as LZMA, just less severe. Worth flagging in the `MAN-08`
  handoff so it's not assumed to have the same fixture strength as BZ2.
